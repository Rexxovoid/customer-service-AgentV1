# 数据扩充与RAGFlow导入说明

更新日期：2026-10-23。批次：EXP-20261023-V1。

## 数量口径

每类新增3400条：2400条模拟订单、500条模拟工单、500条Markdown问答。
三类共10200条，其中8700条追加到既有JSON，1500条以Markdown条目保存。
每类500条问答由60条商品资料问答、20条故障条件问答和420条售后规则场景组成。
420条规则场景采用20个主题×21种条件，不是420条独立法规；问答与原数据共享事实依据，不是新增1500条独立事实。
两份基础文档和来源登记等辅助材料不计入10200条。

## 文件用途

- orders.json：原有60条保留，新增7200条；启动后现有订单工具即可精确查询。
- tickets.json：原有18条保留，新增1500条；为未来工单接口测试准备，当前Agent没有工单查询工具。
- ragflow_knowledge/*_01_商品事实问答.md：历史商品资料，品牌/型号/商品ID和来源明确。
- ragflow_knowledge/*_02_故障条件问答.md：每类20条，有来源性质、适用条件、一次方案与交接边界。
- ragflow_knowledge/*_售后规则场景_*.md：每类420条条件式售后问答，分3册，包含规则ID和来源。
- ragflow_knowledge/00_售后规则依据与能力边界.md：法定规则摘要与项目处理规则的边界。
- ragflow_knowledge/00_品类售后材料清单.md：耳机、鼠标、键盘交接材料的项目建议，不是品牌政策。
- metadata.json：JSON及Markdown的分项统计；manifest.json：相对路径、字节数、SHA-256清单。
- validation_report.json：旧转换记录保留，新增独立批次校验，不把计划写成已验证功能。

## 订单查询示例

```powershell
uv run orderagent --user-id LOAD-HP-U-0001 --order-id LOAD-HP-O-000001
uv run orderagent --user-id LOAD-MS-U-0002 --order-id LOAD-MS-O-000002
uv run orderagent --user-id LOAD-KB-U-0003 --order-id LOAD-KB-O-000003
```

编号前缀HP=耳机、MS=鼠标、KB=键盘。每类120个用户，每个用户20条新增订单。
例如第一条订单仅属于对应LOAD-*-U-0001，使用DEMO-U-001查询它应返回ORDER_NOT_FOUND。
金额、物流号、用户ID和工单状态全部为模拟；所有新订单商品身份取自既有真实来源历史目录。
所有扩充记录带generation_batch；不包含真实姓名、电话、地址、账号或支付凭据。

## 建议导入步骤

1. 只上传ragflow_knowledge目录的Markdown正文。不要把orders.json、tickets.json、元数据、清单或本说明当作通用知识导入。
2. 先导入两份00_基础文档，再按商品、故障和规则案例分别建立知识集合或使用对应元数据。
3. 保留品类、知识类型、来源ID、规则ID和版本；按当前RAGFlow v0.25.4可用的解析方式核对实际效果，不假定YAML元数据会自动变成过滤条件。
4. 先试导入少量文件，并检索完整条目，确保问题、适用条件、答案、来源与边界没有被切散。
5. 商品资料不代表当前在售/售价/库存；模拟指导与官方摘要分别标明。法定权利不能被项目规则缩减。
6. 当前Agent仍从JSON查质量知识；生成Markdown不等于已经接通远程RAGFlow，也没有自动上传服务器。

## 避免评测泄漏

这些Markdown问答用于知识库，不作为独立测试集。规则案例共享R01-R20及C01-C21场景族，不能随机拆分同一模板后声称泛化准确率。
后续效果评测需另写未入库的问题，并按规则族/场景族留出；性能压测可用模拟订单，但不能把订单条数当作并发能力。
可测试未知订单号、错误用户身份、重复请求、空查询等负例；不向运行JSON混入无效结构或真实隐私。
